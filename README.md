# 홀덤 GTO 스튜디오

GTO Wizard처럼 **미리 풀어둔 솔루션을 바로 탐색**하고, 그 솔루션으로 연습·분석까지 하는 홀덤 학습 웹앱입니다. 서버 없이 브라우저가 모든 계산을 합니다. 엔진은 전부 이 저장소에서 TypeScript로 새로 작성했습니다(외부 솔버 코드·데이터 없음).

배포: https://thstjdals09-lang.github.io/gto-studio/ (공개 저장소 `thstjdals09-lang/gto-studio`에는 빌드 결과물과 라이브러리 데이터만 올라갑니다)

| 도구 | 에퀴티 계산기, ICM·버블 팩터, 에퀴티 러시, HU 프리플랍 랩 |

## 라이브러리

| 종류 | 범위 | 방법 |
| --- | --- | --- |
| 프리플랍 | **토너먼트 8맥스 앤티 6·10·15·25·40·60bb**, 캐시 6맥스 100bb(보조) | `src/engine/ring.ts`: 169 핸드 클래스 DCFR, 칩 EV 기준(ICM 미반영). 오픈·림프·콜·3벳(25bb 이하 리셔브 포함)·4벳·올인 트리, 자발적 참여 3명 상한, 올인에는 3인까지 콜 가능. 플랍 이후 가치는 에퀴티×실현계수 근사이고, 실현계수는 자체 포스트플랍 솔버로 15·40·100bb BTN vs BB 플랍 25개를 풀어 측정한 SPR별 값(IP/OOP 비율 1.06→1.18→1.34, 약한 핸드일수록 덜 실현하는 기울기, 플레이어빌리티)으로 보간. 3인 팟은 쌍별 승률 곱을 핸드별로 정규화하고 지수 0.65로 보정(3인 몬테카를로 대비 오차 약 0.02~0.03) |
| 포스트플랍 | 토너먼트 40bb: BTN 오픈 vs BB 콜 24플랍, CO·UTG 오픈 vs BB 콜, SB 림프 vs BB 체크, BTN 오픈·BB 3벳·BTN 콜 각 12플랍 | `src/engine/solver.ts`: 헤즈업 DCFR 풀 트리. 플랍 33% 벳·60% 레이즈(SRP는 오픈한 쪽만 벳, 3벳·림프 팟은 양쪽), 턴 66%, 리버 75%(턴·리버 레이즈 없음). 레인지는 프리플랍 라이브러리에서 그대로 가져옴. 플랍당 100회 또는 익스플로잇어빌리티 0.2%(보조 매치업 80회·0.3%)에서 정지 |

플랍·턴 노드는 콤보별 전략(1바이트)과 EV(2바이트)로 저장되고, 리버는 브라우저가 그 지점 레인지로 리버 서브게임을 재솔브합니다(`src/worker/libspot.ts`).

## 솔버 SDK (공유용)

`sdk/`는 이 엔진을 다른 앱에 넣어 쓰는 독립 패키지(holdem-gto-solver)입니다. 라이브러리 조회, 핸드 분석, 병렬 커스텀 솔브, 노드 잠금, 저장·불러오기를 API로 제공합니다. `npm run sdk:build`로 빌드하고 `npm run sdk:pack`으로 `release/holdem-gto-solver-<버전>.tgz`를 만듭니다. 배포본은 비공개 저장소 `thstjdals09-lang/gto-solver-sdk`의 릴리스에 있습니다. 사용법은 `sdk/README.md`, `sdk/API.md`, `sdk/DATA.md`를 보세요.

## 행동 결정 모델

지금 상황을 주면 내 차례의 액션별 빈도·EV와 추천 액션을 기본 5초 안에 돌려줍니다(`budgetMs` 로 조절, 4초 아래면 짧은 예산용 설정) (`src/lib/decide.ts`, SDK 에서는 `GtoLibrary.decide()`). 2~8명, 6·10·15·25·40·60bb 표 가운데 내 스택에 가장 가까운 것을 씁니다. 6bb 표는 푸시/폴드(+SB 림프), 10bb 표는 미니 오픈과 올인이 함께 있습니다(이 두 표는 결정 모델용이고 앱의 스터디 메뉴에는 아직 없습니다).

```bash
npm run decide -- 상황.json             # 워커 스레드 (코어 수 − 1)
npm run decide -- 상황.json --threads 0 # 한 스레드
```

```json
{
  "players": 8, "hero": "BTN", "cards": "AsKd", "stack": 40,
  "preflop": [
    { "pos": "UTG", "type": "fold" }, { "pos": "UTG1", "type": "fold" }, { "pos": "LJ", "type": "fold" },
    { "pos": "HJ", "type": "fold" }, { "pos": "CO", "type": "fold" },
    { "pos": "BTN", "type": "raise", "to": 2.2 }, { "pos": "SB", "type": "fold" }, { "pos": "BB", "type": "call" }
  ],
  "board": "Ks7d2c",
  "flop": [{ "pos": "BB", "type": "check" }]
}
```

액션은 내 차례 직전까지만 넣습니다. `to`는 그 스트리트에서 그 자리가 넣은 총액(bb)입니다. 8명보다 적으면 앞자리부터 비어 있는 것으로 봅니다(6명이면 LJ가 첫 자리).

| 스트리트 | 방법 | 믿을 만한 정도 |
| --- | --- | --- |
| 프리플랍 | 미리 푼 8맥스 라이브러리 조회 | 라이브러리와 같음 |
| 리버 | 넘어온 레인지로 끝까지 풀기 | 주어진 레인지 안에서는 수렴 (익스플로잇 0.1% 안팎) |
| 턴 | 깊이 제한: 턴 베팅을 풀고, 잎마다 리버 16장(2.5초 예산이면 8장)을 딜해 리버 베팅(75% 한 크기)까지 푼 뒤 쇼다운 (`src/engine/lookahead.ts`) | 근사. 끝까지 푼 해 대비 손실 아래 표 |
| 플랍 | 깊이 제한: 플랍 베팅을 풀고, 잎마다 (턴, 리버) 20쌍(2.5초 예산이면 12쌍)을 딜해 두 스트리트 베팅을 팟 크기 한 라운드로 합쳐 푼 뒤 쇼다운 | 근사. 아래 표. 2.5초 예산에 하위 솔버(`ports`)가 없으면 예전 한 스트리트 근사(`src/engine/street.ts`) |

깊이 제한 풀이의 잎은 실제 카드를 딜해 정확한 쇼다운으로 끝나서, 예전 "에퀴티 × 실현 모델" 잎처럼 상대 레인지 모양(넛 우위·양극화)을 놓치지 않습니다. 런아웃은 표본이지만 대조 변량(런아웃마다 체크다운 값을 빼고 핸드 쌍 승률 행렬로 구한 정확한 평균을 더함)으로 표본 운을 지웁니다. 런아웃 계산은 하위 솔버(SDK 의 `nodeSubPorts`·`browserSubPorts`, `DecideOptions.ports`)에 나눠 맡길 수 있고, 명령줄은 기본으로 워커 스레드를 씁니다. 지나온 스트리트를 처음 다시 풀 때(레인지만 필요)는 시간이 짧아 한 스트리트 근사를 씁니다.

정답과 비교한 손실 (`npm run bench:decide`, 2026-11-18, 6코어): gto-studio 배포 라이브러리(같은 트리를 리버까지 끝까지 푼 해, 익스플로잇 약 0.2%)를 정답으로 두고, 각 노드에서 빠른 풀이의 전략이 정답 EV 보다 잃는 양을 노드 팟 대비 %로 잰 평균입니다(그 뒤는 정답대로 친다고 봄). 플랍은 BTN vs BB·3벳 팟 36개 플랍 113노드, 턴은 8개 플랍 × 2개 라인 × 2장 127노드. 결정 모델의 트리는 라이브러리 트리보다 커서(잎 11개, 라이브러리는 3개 안팎) 같은 시간에 반복이 적으므로, 시간 열은 결정 모델 트리에서의 반복 수에 맞춘 값입니다.

| 예산 | 스트리트 | 예전 (한 스트리트 근사) | 깊이 제한, 한 스레드 | 깊이 제한, 워커 5개 |
| --- | --- | --- | --- | --- |
| 2.5초 | 플랍 | 1.00% | (쓰지 않음: 반복이 모자라 14회 1.15%) | 0.73% (1초 상당, 48회) |
| 2.5초 | 턴 | 0.83% | 0.64% (0.5초 상당, 17회) | 0.18% (1.5초 상당, 62회) |
| 5초 (기본) | 플랍 | 1.00% | 0.69% (1.2초 상당, 46회) | 0.64% (3.2초 상당, 133회) |
| 5초 (기본) | 턴 | 0.83% | 0.16% (1.2초 상당, 47회) | 0.10% (3.2초 상당, 137회) |

정답 자체의 오차(라이브러리 전략의 손실)는 플랍 0.05%, 턴 0.07%입니다. 플랍의 남은 손실 대부분은 턴·리버 베팅을 한 라운드로 합친 근사에서 옵니다(턴 라운드와 리버 라운드를 따로 두면 같은 시간에 반복이 너무 적어 더 나빴다).

3~4명 팟은 남은 사람을 모두 넣어 멀티웨이 솔버(`src/engine/multi.ts`, `src/lib/decideMulti.ts`)로 풀고, 스트리트마다 모든 사람의 레인지를 실제 액션대로 좁혀 다음 스트리트로 넘깁니다(예전에는 나와 주 상대 한 명의 승부로 줄여 셋째 사람의 레인지가 좁혀지지도 않았습니다). 트리는 인원 수만큼 커져서 한 크기로 줄입니다: 플랍 33%·턴 66%(레이즈 60%) 베팅을 풀고 잎에서 (턴, 리버) 10쌍·리버 8장을 딜해 체크다운, 리버는 33·75%(레이즈 60%)로 끝까지. 3인 쇼다운은 상대끼리의 카드 겹침을 무시한 근사입니다(정확한 계산은 수십 배 느림). 한 명이 폴드해 둘이 남으면 그 뒤 스트리트는 위의 헤즈업 풀이로 넘어가고, 5명 이상은 예전처럼 둘의 승부로 줄입니다. 3인 턴을 리버 44장 전부·리버 베팅(75%)까지 2분 동안 푼 해와 비교하면 노드당 손실은 평균 1.0%였고(CO 오픈·BTN 콜·BB 콜 레인지, 턴 3개 × 노드 3개), 드로우가 많은 연결 보드(Ts9d4c2s)에서 2~3%로 가장 컸습니다(2.5초, 반복 13~28회). 5초 예산이면 반복이 77~102회로 늘어 평균 0.40%(연결 보드 0.65%)였습니다. 같은 5초에 리버 베팅을 넣은 잎(리버 4~6장)은 반복이 20~35회로 줄어 0.68~0.78%로 오히려 나빴습니다. 결과의 `notes`에 그 결정에 쓰인 근사가 적혀 나옵니다. 시간 안에 수렴하지 못한 답(익스플로잇 1% 초과)에도 안내가 붙습니다. 다른 프로그램이 CPU를 쓰는 동안에는 리버가 400회 대신 10회만 돌 수 있습니다.

### 상대 성향 반영 (`reads`)

기본값은 "상대도 GTO 레인지로 친다"는 가정입니다. 상대가 균형에서 크게 벗어나 있으면 이 가정이 틀려서 답도 틀립니다. 입력에 `reads`를 넣으면 프리플랍에서 그 상대의 레인지를 넓히거나 좁혀서 보고, 내 액션은 그 상대에게 EV가 가장 큰 것을 고릅니다(`source: "exploit"`).

```json
{ "reads": { "*": { "call": 2 }, "BTN": { "raise": 3 } } }
```

키는 자리 이름이나 `"*"`(모두)이고, 값은 GTO 대비 배수입니다(1 = GTO, 2 = 두 배 자주, 0~10). `"*"`와 자리별 값은 합쳐집니다. 배수는 그 상대의 모든 프리플랍 결정(오픈·3벳·4벳·올인 콜)에 똑같이 적용됩니다. 늘어나는 범위는 GTO EV로 봤을 때 그 액션에 가장 가까웠던 핸드부터 채웁니다(`src/lib/exploit.ts`).

성향이 맞다는 전제에서, GTO 빈도 그대로 칠 때와 비교한 이득입니다(전체 핸드 평균, `mtt8-6`·`mtt8-25` 표).

| 상황 | GTO 그대로 | 성향 반영 | 추천이 바뀌는 핸드 |
| --- | --- | --- | --- |
| 7bb BTN 첫 진입, 블라인드가 올인 콜을 0.3배만 | 0.83bb | 1.46bb | 50% |
| 7bb BTN 첫 진입, 블라인드가 올인 콜을 2배 | 0.69bb | 0.70bb | 4% |
| 7bb BB, BTN이 올인을 2배 | 1.54bb | 1.77bb | 31% |
| 7bb BB, BTN이 올인을 0.4배만 | 0.25bb | 0.37bb | 30% |
| 25bb BTN 첫 진입, 블라인드가 콜을 2배 | 0.44bb | 0.71bb | 23% |

한계: 성향은 프리플랍 레인지에만 반영됩니다. 포스트플랍에서 상대가 벳·콜하는 방식은 여전히 GTO로 가정합니다(넓어진 레인지는 포스트플랍 풀이에 넘어갑니다). 배수가 실제와 다르면 GTO보다 나쁜 답이 나옵니다. 오픈 림프처럼 트리에 없는 액션은 성향으로도 다루지 못합니다.

### 표에 없는 프리플랍 흐름 (`source: "allin-equity"`)

실전 기록(2026-11-17, 15개 대회 887번의 프리플랍 결정)을 되돌려 보니 44번(5%)은 엔진이 예외를 던졌고, 그러면 호출하는 쪽이 제멋대로 판단해 다중 올인 팟에 73o·J9o 로 스택 전부를 콜하는 일이 생겼습니다. 이제 다음 흐름은 예외 대신 답을 돌려줍니다.

| 흐름 | 처리 |
| --- | --- |
| 기록에 액션이 없는 자리(자리 비움·관측 누락) | 폴드로 보고 계속 (`notes`에 표시) |
| 올인 위에 더 큰 올인처럼 표에 레이즈가 없는 자리의 레이즈 | 콜로 보고 표를 계속 따라감 (넣은 돈은 그대로) |
| 림프 팟의 BB 처럼 표가 끝났는데 내 차례인 경우 | 콜할 돈이 없으면 체크 |
| 내가 림프한 뒤 올인을 받는 것처럼 표가 내 차례에 닿지 못한 경우 | 상대 레인지 대 내 승률(몬테카를로, `multiwayEquity`)과 **내가 이길 수 있는 메인팟**(각자 넣은 돈 중 내 총 투자까지)으로 콜·폴드만 계산. 표로 좁히지 못한 상대는 무작위 핸드 상대 승률 상위 20% 핸드로 봄. 아직 행동하지 않은 뒷자리는 폴드한다고 봄 |
| 표가 4명 이상 팟을 만들지 않아(`maxPlayersInPot: 3`) 내 자리에 폴드밖에 없는 경우 | 바로 위와 같은 승률 계산 |
| 돈을 넣은 상대가 2명 이상인 올인을 마주했는데 표가 폴드를 고른 경우 | 표는 다자 올인을 쌍별 승률 곱으로 근사해 강한 핸드를 낮게 본다. 돈을 넣은 상대 전원이 넣은 돈만 들고 쇼다운까지 간다는 보수적 승률(표본 8000)로 다시 재서 팟의 1.1% 넘게 이득이면 콜. 콜을 폴드로 바꾸지는 않음 |

GTO 라인이라면 오지 않는 노드(예: SB 가 AA 로 콜한 뒤 올인을 받음)에서는 표에 저장된 그 핸드의 빈도가 학습되지 않은 균등값(폴드 50%·콜 50%)입니다. 이때는 빈도 대신 표의 EV 가 가장 큰 액션을 고릅니다(`source: "library"`, `notes`에 표시).

2026-11-17 "이상한 자리에서 AA·KK 가 폴드한다"는 신고로, 모든 표(6·10·15·25·40·60bb)의 모든 노드 32,316곳에 AA·KK 를 앉혀 `decide`를 돌려 봤습니다. 표에서 AA·KK 의 가장 높은 빈도가 폴드인 노드는 5,624곳이었습니다(균등 빈도 동점에서 0번=폴드, 4명째 자리의 강제 폴드, 다자 올인 근사). 고친 뒤 AA 폴드는 0곳입니다. KK 폴드는 25bb 이상에서 781곳 남는데, 모두 "오픈→3벳→4벳→콜드 5벳 올인"처럼 올인 쪽 레인지가 AA 위주인 자리이고, 보수적 승률로 다시 재도 콜이 손해인 곳입니다.

같은 기록으로 다시 돌리면 엔진 쪽 예외는 44번에서 0번이 되고(남는 것은 입력의 자리 이름 오류뿐), 가장 크게 잃은 "BB AQo 로 두 올인에 86bb 콜"은 폴드가 됩니다. 이 경로는 레이즈를 판단하지 않고 빈도도 0/1 뿐이라 GTO 해가 아닙니다. 액션의 자리 이름이 표에 없으면(`pos` 누락 등) 돈을 빠뜨리고 틀린 답을 내므로 예외로 알립니다.

## 생성

```bash
npm install
node_modules/.bin/esbuild scripts/gen-preflop.ts --bundle --platform=node --format=esm --outfile=.cache/gen-preflop.mjs
# (선택) 실현율 재측정: 포맷별 BTN vs BB 플랍을 풀어 핸드별 실제 팟 몫을 기록한 뒤 표를 맞춘다
node_modules/.bin/esbuild scripts/calib-realization.ts --bundle --platform=node --format=esm --outfile=.cache/calib.mjs
node .cache/calib.mjs mtt8-40 8 30 12 0 1      # 포맷, 플랍 수, 반복, 시드, 샤드
node_modules/.bin/esbuild scripts/fit-realization.ts --bundle --platform=node --format=esm --outfile=.cache/fit.mjs
POOLED_ONLY=1 node .cache/fit.mjs              # 출력된 표를 ring.ts 의 REALIZATION_TABLE 에 넣는다
node .cache/gen-preflop.mjs "" 300            # 프리플랍 5개 포맷 (에퀴티 행렬 포함, 포맷당 10~40분)
node_modules/.bin/esbuild scripts/gen-postflop.ts --bundle --platform=node --format=esm --outfile=.cache/gen-postflop.mjs
bash scripts/run-postflop.sh 0 4 &            # 샤드 0..3 병렬 (6코어 기준 수 시간)
node_modules/.bin/esbuild scripts/gen-index.ts --bundle --platform=node --format=esm --outfile=.cache/gen-index.mjs && node .cache/gen-index.mjs
```

포스트플랍 데이터(`public/lib/postflop/`, 약 250MB)는 소스 저장소에 넣지 않고 배포 저장소에만 올립니다.

## 한계

- 프리플랍은 포스트플랍을 직접 풀지 않는 근사라 상용 솔루션과 차이가 있습니다. 실현계수는 측정값이지만 플랍 표본이 작습니다.
- 토너먼트 솔루션은 칩 EV 기준이며 ICM(상금 구조)을 반영하지 않습니다. 스택은 모두 같다고 가정합니다.
- 포스트플랍 라이브러리는 단일 사이즈 트리이고 플랍 수가 제한적입니다. 그 밖의 보드·라인은 솔버 메뉴에서 직접 풉니다.
- 분석기는 라이브러리 트리에 없는 사이즈·라인에서 채점을 멈춥니다. 토너먼트 핸드는 유효 스택에 가장 가까운 깊이(15·25·40·60bb)로, 8인보다 적은 테이블은 뒷자리 기준으로 맞춰 근사합니다.
- 멀티웨이 커스텀 솔브는 4인 이상 쇼다운이 근사이고 번칭 효과를 반영하지 않습니다.
- 행동 결정 모델의 플랍은 턴·리버 베팅을 한 라운드로 합친 깊이 제한 근사이고(끝까지 푼 해 대비 노드당 0.6~0.7%), 하위 솔버가 없으면 예전 한 스트리트 근사를 씁니다. 3~4명 팟의 플랍·턴은 뒤 스트리트를 체크다운으로 보는 근사(뒤에 베팅이 없다고 봄)이고 한 크기 트리이며, 2.5초 예산의 플랍은 10회 안팎밖에 못 돌아 수렴이 덜 될 수 있습니다(5초면 70~130회). 5명 이상 팟은 주 상대 한 명과의 승부로 줄여 풉니다.
